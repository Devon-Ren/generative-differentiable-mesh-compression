One 500-step interval, explained from scratch

Scene room, requested size 10 MB, the interval from step 9000 to step 9500. Numbers marked (log) are from the real run; numbers marked (est.) are filled in so the arithmetic can be followed end to end.

What the system is, in one paragraph

You give it photos of a room and one number: "the file must be 10 MB." It gives back a triangle mesh file of about 10 MB. MeshSplatting trains a mesh that grows: every 500 steps it picks some triangles and cuts each into four. The original picks them by a rule of thumb, and the final file size is whatever it turns out to be. We change one thing: every 500 steps, first compute how many vertices the 10 MB can pay for, then how many triangles to cut this round, and only then set the cut-off line λ so that exactly that many triangles pass. λ is not an input. It is computed.

What is in hand at step 9000, right after that round's cut

  • A pile of loose triangles (each owns its three vertices, nothing shared yet). About 1 010 000 vertices (est.).
  • λ_now = 1.93 × 10⁻³ (log): the line that will be used at 9500. It was drawn at 9000.
  • σ = 0.46, yield = 0.88, b_v = 6.42 B, overhead = 0.649 MB, all measured (log).
  • An error ledger with one row per triangle, just wiped to zero.

The recursion

── steps 9000 → 9500: ordinary training, 500 times ─────────────────────────────
for each step:
    take one training photo, render the scene with the current triangles
    compare render and photo pixel by pixel → an error per pixel
    charge each pixel's error to the triangle that painted that pixel      ← ΔD_t accumulates
    backprop; Adam updates positions, colours, opacities              ← upstream, unchanged

── step 9500: the decision ──────────────────────────────────────────────────────
1  upstream pruning: drop triangles too transparent, too big on screen,
   or that no pixel relies on                                      → V = 919 243

2  read the ledger:   ratio_t = ΔD_t / ΔR    for every triangle (ΔR = 33 B)

3  how many vertices can the aim pay for?
       V* = (aim − overhead) / (b_v + fpv · b_f)
          = (12.5 MB − 0.649 MB) / (6.42 + 2.5 × 2.0) B             → V* = 1 037 451

4  how many triangles to cut this round?
       growth factor  f = (V*/V)^(1/remaining) = 1 037 451 / 919 243  → f = 1.1286
       vertices to add    V · (f − 1) = 919 243 × 0.1286            → 118 208
       one cut adds 3 vertices, σ of them survive → net per cut 3 · σ = 1.38
       desired = V · (f − 1) / (3 · σ) = 118 208 / 1.38              → 85 349

5  cap = min(upstream's own limit, desired) = min(248 195, 85 350)  → 85 350

6  cut every triangle with ratio_t > λ_now, at most cap of them
       83 177 pass the line, 83 611 cut (plus upstream's 100 largest)
       each cut: 3 new vertices at the edge midpoints, 1 → 4       → V = 1 163 690

7  set the line for the NEXT round
       V_exp        = V + σ · (vertices just added)     count expected after next pruning
                    = 919 243 + 0.46 × 244 447                      → 1 031 700 (est.)
       desired_next = line 4 again, from V_exp, remaining − 1        → 0 (no round left)
       k_asked      = desired_next / yield                           → 0
       λ_next = the k_asked-th largest ratio_t                     → k = 0: keep λ = 1.93e-3

8  wipe the ledger, resize it to the new triangle count

── steps 9500 → 10000: repeat the training loop ────────────────────────────────

Why each line is there

The ledger (the training loop)

Line 3: the byte table, and why it is solved backwards

file bytes = b_v · V + b_f · F + overhead
Every vertex costs b_v bytes, every face costs b_f bytes, plus the box. In the finished mesh F ≈ fpv · V, so the file is a straight line in V: (b_v + fpv·b_f) · V + overhead. The user hands us bytes; the only knob the system has is "how many triangles to cut", which is a count. So solve the line for V: that is V*, the number of vertices the budget buys.
b_v and overhead are not guesses. From step 4500 on, every 1000 steps, the current triangles are copied, cleaned the way step 30k will clean them, and run through the real file encoder. The stream sizes it writes give b_v and overhead. The copy is thrown away; training never notices.
Why aim at 12.5 and not 10. At step 9500 three things are invisible: the final cleaning at 30k will drop about 10 % of the vertices; once stitched into a mesh the connectivity costs less per vertex than the prior 5 B; and b_v read on loose triangles is slightly high. All three make the final file smaller than the formula says, and after step 10k nothing can ever add bytes again, only remove them. So the growth phase deliberately overshoots by 25 % and the second half trims back with the real encoder measuring every round. This 1.25 is a calibrated number, one value for all Mip-NeRF / T&T scenes, 1.1 for Blender.

Line 4: why grow geometrically instead of cutting everything at once

desired = V · ((V*/V)^(1/remaining) − 1) / (3 · σ)
Freshly cut triangles need training before anyone knows if they are useful, and about half of them (σ = 0.46) are pruned at the next round. Cutting everything at once would dump a huge batch of untrained triangles that die together. So the gap to V* is spread as equal ratios over the remaining rounds: 5 rounds left and V must double → each round grows by 2^(1/5) = 15 %. The plan is recomputed every round, so when the byte table moves, V* moves and the plan follows.

Lines 6 and 7: what λ really is

λ_next = k_asked-th largest ratio_t,   k_asked = desired_next / yield
This is why the user never sees λ: it is just "how many to cut this round" written as a threshold. Redrawn every 500 steps from the scene's own chart.

Line 6: what a cut is

The second half: the same recursion, run in reverse (step 16000 → 16500)

After 11k the triangles are stitched into a mesh and can no longer grow. Every 500 steps from 12500 to 19500 the following runs. room 10 MB, real numbers unless marked.

── 16000 → 16500: training, ledger as before (ΔD per face) ──────────────────────
── step 16500 ─────────────────────────────────────────────────────────────────
1  copy the mesh, clean it as 30k will, run the real encoder  → "delivered today": 9.96 MB (est.)
       refresh the byte table: b_v 5.9  b_f 1.8  overhead 0.65 MB  (log)
2  that number has been rising (14000: 9.05 → 16000: 9.93); extend the trend
   to step 24000, where opacities stop changing                 → landing ≈ 10.3 MB
3  excess = landing − target = 0.3 MB
   one edge collapse saves  b_v + 2·b_f ≈ 9.5 B
   pairs = 0.3 MB / 9.5 B ≈ 32 000, over the 7 rounds left      → ≈ 4 500 this round
4  if landing ≤ target: do nothing this round  (12500–16000: 8 rounds, no edit)
5  score every edge (u,v):  score_uv = ΔD_uv / ΔR_uv
       ΔD_uv = error of all faces touching u or v   (how much the merge would hurt)
       ΔR_uv = bytes the file loses: b_v if both ends are delivered
               + b_f per delivered face on the edge
6  collapse the lowest scores first: merge u and v into their midpoint,
   average position, colour, opacity and Adam momentum   → optimiser keeps its memory
   one vertex per round, never flip a face, at most 15 % of V
7  record the bytes actually removed, for the next round's trend
── repeat to 19500; 20k upstream supersampling, 24k fully opaque, 30k cleaning → encode → 10.29 MB ──
collapse (u,v) if ΔD_uv / ΔR_uv < λ    (the growth rule read backwards: cut if ΔD_t / ΔR_t > λ)
Growth cuts triangles whose error is large per byte; trimming merges vertices whose error is small per byte. Same λ, same ledger, same price tags. The 25 % packed as margin is removed here while the real encoder measures every round. room ends at 1.029 × target, with picture quality 0.03 dB from the fixed-λ curve at the same bytes.

One sentence

The user gives one number, the megabytes. Every 500 steps the real encoder prices a vertex, the byte table turns the budget into a vertex count, the plan turns that into "cut k triangles this round", and λ is simply the height of the k-th bar. In the second half the same λ is read backwards to merge what the margin over-bought. λ, V*, the prices: all computed during training. The one number a human chose is the 25 % margin.
